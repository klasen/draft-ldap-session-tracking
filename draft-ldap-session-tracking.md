--- abstract

Many network devices, application servers, and middleware components of an enterprise software infrastructure generate session tracking identifiers. These identifiers are useful when analyzing activity and accounting logs to group activity relating to a particular session. This document describes how Lightweight Directory Access Protocol version 3 (LDAP) clients can include session tracking identifiers with their LDAP requests by using controls. An LDAP server receiving these controls can include the identifiers in its log messages, enabling LDAP requests to be correlated with activity in logs of other infrastructure components. The control also enables session tracking information to be generated by LDAP servers and returned to clients and other servers. Three formats of session tracking identifiers are defined.

# Introduction {#intro}

Most directory server implementations produce access logs that detail each request they receive. These logs can be read using log parsing tools or specialized log viewer applications. For each logged request, it is typically possible to determine the bind DN, or another form of authentication identity, of the client that sent the request. Many servers also log the client's IP address.

In the original OSI architecture, users were expected to interact with a directory service through specialized applications known as Directory User Agents, which were clients of the Directory Access Protocol. Similarly, in early Internet directory deployments, most LDAP clients were desktop applications used to search an enterprise directory for address book or contact information.

Today, most LDAP clients are embedded in middleware and server applications. Legacy address book protocols might be gatewayed into LDAP, or a server might consult an LDAP server to check a user's password or obtain their preferences. Although LDAP requests might result from a user's activity elsewhere on the network, the user is rarely 'driving' the LDAP client and is often unaware that LDAP requests are being generated on their behalf.

This information is important to directory system administrators and auditors, who may wish to determine who is using the directory service or track the source of unusual requests.

When a directory server is accessed only by middleware, and end users interact with that middleware through other kinds of servers such as application servers or remote access servers, it can be difficult to correlate the directory server's log with the logs of those other servers to determine why LDAP requests were made and who caused them. Reasons include:

- Directory servers can perform hundreds of requests per second or more. Even with time synchronization, request times might not be logged accurately enough for correlation; server logs might have only one-second resolution.
- A single middleware function, such as authenticating a user, can generate multiple LDAP requests.
- High-performance middleware commonly uses connection pooling: it manages persistent connections to each directory server and multiplexes operations across them. Connections share the same source IP address and bind DN, and LDAP's asynchronous protocol allows multiple requests to be in progress on each connection and responses to be processed in a different order. Requests resulting from one activity can also be sent over different connections.

This document defines a control for LDAPv3 operation requests. The control carries session tracking information that can correlate information in directory server logs with logs from other middleware servers. LDAPv3 is specified in {{RFC4510}}. The words "MUST", "SHOULD", and "MAY" are to be interpreted as described in {{RFC2119}}.

## Motivation for session tracking

A typical enterprise deployment in which an application indirectly relies on a directory might resemble:

~~~txt
  +------+     +--------+       +----------+      +--------+
  | User |     | Appli- |       | Auth./   | LDAP |  LDAP  |
  |      +-----+ cation +-------+ Identity +------+ Server |
  |  A   |     | Server |       | Provider |      |   D    |
  +------+     |   B    |       |    C     |      +--------+
         +--------+       +----------+
~~~

A user (A) makes a request to an application server (B). The application server might rely on an integrated or external authentication provider to check the user's credentials, or use an identity provider to obtain profile information. This request might use an API or a protocol other than LDAP, such as RADIUS, Kerberos, or SMB. The authentication or identity provider (C) generates one or more LDAP requests and sends them to an LDAP server (D).

The LDAP server already has the IP address and authentication credentials of the authentication or identity provider. If the provider includes the Proxied Authorization Control {{RFC4370}}, the LDAP server might also receive the distinguished name or authorization identity of the user (A) or application server (B), depending on how the provider uses the directory. However, the provider might need to perform one or more LDAP search or bind requests to obtain that distinguished name. If the user or application server has no corresponding directory entry, the base LDAP specification and the Proxied Authorization Control provide no way for the provider to describe that identity to the LDAP server.

If the application server or authentication/identity provider has generated a session identifier for tracking a user's interactions, it is useful to include that information with requests to the directory server so that the identifier appears in the directory server's logs. That is the purpose of the control defined in the next section.

# Control Definition

There is no standard way to describe a session. Session identifier formats differ, and each application that tracks sessions typically has its own semantics. The control is therefore extensible to accommodate different application concepts and formats.

The value of the session identifier control contains four pieces of information: `sessionSourceIp`, `sessionSourceName`, `formatOID`, and `sessionTrackingIdentifier`.

`sessionSourceIp` is a US-ASCII string encoding of an IPv4 or IPv6 address {{RFC1884}} for the component that generated the session tracking identifier. This field lets a directory server administrator identify the system managing the session, even without a log parser for the identifier's format. There is no guarantee of IP-level connectivity between the directory server and that system. If Network Address Translation is used, this address might be from a private-use range.

`sessionSourceName` is a UTF-8 {{RFC3629}} encoded ISO 10646 {{ISO10646}} text string describing the component that generated the identifier. Its format is determined by `formatOID`; examples include a hostname, a distinguished name, or a web service address. It identifies the server using a name other than its IP address and is not intended to identify an end user.

`formatOID` is a US-ASCII dotted-decimal representation of an OBJECT IDENTIFIER. It identifies the scheme used for `sessionSourceName` and `sessionTrackingIdentifier`. As there is no standard scheme for session information, many formats are expected. This document defines three.

`sessionTrackingIdentifier` is a UTF-8 encoded ISO 10646 string. The identifier SHOULD be limited to whitespace and printable characters. Non-printing and control characters SHOULD NOT be used, and byte sequences that are not valid UTF-8 MUST NOT be used. The format identified by `formatOID` defines the identifier's syntax and semantics, including how values are compared for equality. An identifier might be a decimal counter, a username, a timestamp, a fragment of XML, or another value.

## Formal definition

This document defines one LDAP control. The `controlType` is `1.3.6.1.4.1.21008.108.63.1`, the criticality MUST be either FALSE or absent, and the `controlValue` MUST be present. The `controlValue` OCTET STRING contains the BER {{X690}} encoding of a value of the following ASN.1 type:

~~~ asn.1
LDAP-Session-Identifier-Control
DEFINITIONS IMPLICIT TAGS ::= BEGIN

LDAPString ::= OCTET STRING -- UTF-8 encoded
LDAPOID ::= OCTET STRING -- Constrained to numericoid

SessionIdentifierControlValue ::= SEQUENCE {
  sessionSourceIp                 LDAPString,
  sessionSourceName               LDAPString,
  formatOID                       LDAPOID,
  sessionTrackingIdentifier       LDAPString
}

END
~~~

The `sessionSourceIp` element SHOULD NOT be longer than 42 characters (the length needed for an IPv6 address string) and MUST NOT be longer than 128 characters. Each character is encoded in one byte. If the generating system's IP address is unknown, this element SHOULD be zero length.

The `sessionSourceName` element SHOULD NOT be longer than 1024 characters and MUST NOT be longer than 65536 bytes. A UTF-8 character MAY be encoded in more than one byte. If no other addressing information is known or relevant to the format, this element SHOULD be zero length.

The `formatOID` element MUST contain only US-ASCII encodings of FULL STOP and DIGIT ZERO through DIGIT NINE (0x2E and 0x30-0x39). It MUST NOT be zero length and SHOULD NOT be longer than 1024 characters.

The `sessionTrackingIdentifier` MAY be zero length, although this might not be useful. There is no upper bound, but values SHOULD NOT exceed 65536 characters without prior agreement with the directory server administrator. A UTF-8 character MAY be encoded in more than one byte.

## Use in LDAP

The control MAY be included in any LDAP operation and has order-dependent semantics.

A client might place the control on a `bindRequest`, `searchRequest`, `modifyRequest`, `addRequest`, `delRequest`, `modDNRequest`, `compareRequest`, or `extendedReq`. A client MAY include multiple controls of this type in one request to incorporate distinct session tracking identifiers in different formats.

When a network service proxies or chains LDAP, receiving a client request and generating one or more requests to other LDAP servers, it SHOULD include any received controls of this type in the generated requests without modification. A service MAY silently remove a control if it violates security policy. If the service has its own session state identifier, it SHOULD append its own control after controls received from the client. When multiple proxies are involved, each adds its own session state to the end of the controls list.

A server might place the control on a `bindResponse`, `searchResDone`, `modifyResponse`, `addResponse`, `delResponse`, `modDNResponse`, `compareResponse`, `extendedResp`, or `intermediateResponse`. A server can include the control whether or not the client included one in the request. Such a response control is unsolicited; clients that do not recognize the control or its format can safely ignore it. A server MAY include multiple controls of this type in a response.

## Extensibility considerations

This document defines three possible formats. Applications MAY define formats for session tracking identifiers already in use. An application or server developer transferring an implementation's format in an LDAP control MUST choose a new, unique OBJECT IDENTIFIER for that format.

The format determines the semantics of `sessionSourceName` and `sessionTrackingIdentifier`.

When an LDAP server with session tracking logging enabled receives one or more of these controls, it SHOULD include all fields of all controls with the request's logging information. An LDAP server that supports third-party or extensible log parsing tools SHOULD NOT reject or ignore a control solely because it does not recognize the `formatOID`; applications might want log parsers to use the information even when the directory server does not.

If an LDAP server does not recognize the control, the control is malformed, or the client is not authorized to use it, the server SHOULD ignore the control and process the request as if it were absent. When an LDAP client receives a response containing this control, it SHOULD silently ignore formats it does not recognize and process the response as if the control were absent.

# Session Tracking Format Definitions

This section defines three formats for the session tracking control: two for RADIUS accounting and one based on usernames. Other documents can define additional formats.

## Formats for use with RADIUS accounting

These formats can be used in LDAP clients that are part of or used by RADIUS servers {{RFC2865}}.

With `formatOID` set to `1.3.6.1.4.1.21008.108.63.1.1`, `sessionTrackingIdentifier` SHOULD contain the value of the Acct-Session-Id RADIUS attribute (type 44), as defined in Section 5.5 of {{RFC2866}}. That section states that Acct-Session-Id SHOULD contain UTF-8 encoded ISO 10646 characters.

With `formatOID` set to `1.3.6.1.4.1.21008.108.63.1.2`, `sessionTrackingIdentifier` SHOULD contain the value of the Acct-Multi-Session-Id RADIUS attribute (type 50), as defined in Section 5.11 of {{RFC2866}}. That section states that Acct-Multi-Session-Id SHOULD contain UTF-8 encoded ISO 10646 characters.

For either format, `sessionSourceIp` SHOULD contain a string encoding of the IPv4 address from the NAS-IP-Address RADIUS attribute (type 4), or the IPv6 address from the NAS-IPv6-Address RADIUS attribute (type 95), as defined in {{RFC3162}}. `sessionSourceName` SHOULD contain the NAS-Identifier RADIUS attribute (type 32), if present, or be zero length if that attribute was not provided or is not in a recognized format.

## Format for username accounting

This format can be used in LDAP clients that are part of applications identifying users with simple string usernames.

With `formatOID` set to `1.3.6.1.4.1.21008.108.63.1.3`, `sessionTrackingIdentifier` SHOULD contain a username that has already been authenticated by the application generating the session. This format SHOULD NOT be used for purported names when the application has not verified that the username is valid.

`sessionSourceName` SHOULD contain the hostname where the application is running, or be zero length if the hostname is unknown.

The username SHOULD be a SASL authorization identity string as described in Section 3.4.1 of {{RFC4422}}. These usernames are expected not to be globally unique, but only unique within a particular application or enterprise. A username need not be a distinguished name, and an implementation receiving a control in this format MUST NOT assume that `sessionTrackingIdentifier` can be parsed as a distinguished name.

Unlike the Proxied Authorization Control {{RFC4370}}, this session identifier control SHOULD NOT influence the directory server's access control decision about whether or how to perform the request.

This format does not distinguish multiple sessions or periods of interaction by the same user. It is intended for deployments that need to tie each directory operation to the identity of the user whose activity caused the request, even if that user is not represented in the directory where the operation is performed.

### Example

If an application server `app.example.com` at IPv4 address `192.0.2.1` has authenticated a user named `bloggs`, and sends a search request to obtain public service configuration information for that user, it might include a session identifier control. Before encoding, the `SessionIdentifierControlValue` ASN.1 value is:

~~~asn.1
{  -- SEQUENCE
   "192.0.2.1",                    -- sessionSourceIp
   "app.example.com",              -- sessionSourceName
   "1.3.6.1.4.1.21008.108.63.1.3", -- formatOID
   "bloggs"                        -- sessionTrackingIdentifier
}
~~~

The session identifier control uses `controlType` `1.3.6.1.4.1.21008.108.63.1`, criticality FALSE, and a `controlValue` containing the BER encoding of the `SessionIdentifierControlValue`. The control in the LDAP request resembles:

~~~asn.1

   "1.3.6.1.4.1.21008.108.63.1", -- controlType
   FALSE,                        -- criticality
   '304204093139322e302e322e31040f6170702e6578616d706c652e636f6d
    041c312e332e362e312e342e312e32313030382e3130382e36332e312e33
    0406626c6f676773'H           -- controlValue
}
~~~

## Formats for use with trace context propagation

These format can be used in LDAP clients that take part in distributed tracing.

With `formatOID` set to `1.3.6.1.4.1.21008.108.63.1.4`, `sessionTrackingIdentifier` SHOULD contain the value of the `traceparent` header, as defined in Section 3.2 of {{W3C-TRACE-CONTEXT-2}}.

With `formatOID` set to `1.3.6.1.4.1.21008.108.63.1.5`, `sessionTrackingIdentifier` SHOULD contain the value of the `tracestate` header, as defined in Section 3.3 of {{W3C-TRACE-CONTEXT-2}}.

For either format, `sessionSourceIp` and `sessionSourceName` SHOULD be zero length.

If an application server sends a modify request to create an entry user, it might include a session identifier control representing its current trace context. Before encoding, the `SessionIdentifierControlValue` ASN.1 value is:

# Security Considerations {#security}

The session identifier controls defined in this document are not security controls or proxy authentication mechanisms, and SHOULD NOT influence operation processing behavior in a directory server.

Malicious clients might use this control to provide false or misleading information in directory server logs. LDAP servers SHOULD implement access checks that limit whether client-provided session identifier information is logged. Servers implementing this control SHOULD allow the administrator to configure it to be ignored unless the request was received from an authenticated client. They SHOULD also allow the administrator to configure it to be ignored unless the client is authorized to use this or related controls, such as the Proxied Authorization Control {{RFC4370}}. Session identifier information from clients that do not meet the server's access check requirements SHOULD be silently discarded.

Some formats might contain personally identifiable information, such as usernames or client IP addresses. Unless data link, network, or transport-level encryption is used, attackers monitoring the network might see this information. LDAP clients that include this control in requests SHOULD support underlying security services that establish connection confidentiality before sending the control, such as a SASL mechanism that negotiates a security layer or the StartTLS operation.

Correlation of activity across multiple servers can let administrators and monitoring tools construct a more accurate picture of user behavior, including the applications and services with which a user has interacted. This control is therefore not appropriate for deployments that intend to anonymize directory requests. Formats containing personally identifiable information SHOULD NOT be used between systems in different organizations without an existing agreement on privacy protection.

A session tracking control might reveal internal IP addresses, hostnames, and other identifiers that expose enterprise network structure. A network service generating its own sessions SHOULD NOT send a session tracking control to a directory server under different administration or in a different security enclave. An LDAP client that also receives session tracking identifiers over another protocol or proxies incoming LDAP requests SHOULD NOT forward received identifiers to a directory server under different administration or in a different security enclave. A packet-inspecting firewall permitting outgoing LDAP requests from an enterprise network SHOULD silently remove session tracking controls sent to directory servers outside that network, unless a pre-existing policy allows sending them to that server.
